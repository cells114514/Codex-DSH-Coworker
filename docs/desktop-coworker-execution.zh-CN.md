# 双桌面 Coworker 通信验证与接入任务书

日期：2026-11-18。交付对象：负责实施的 DSH。

这是待执行任务书，不表示候选项目已在本机验证通过。现有调查见 [Coworker 事件交付评估](coworker-event-delivery-assessment.zh-CN.md)。本任务的重点是 Codex 桌面版与 DSH Desktop 之间的双向协作，不是继续调整 dsh_wait 的轮询间隔。

## 1. 用户目标

用户正常打开两个桌面应用后，可以让两个 Agent 作为同事协作：

1. Codex 向指定 DSH 会话交接工作，然后结束当前模型轮次，不周期调用 wait/status/tail。
2. DSH 独立执行；普通工具日志和进度只在本地程序中处理。
3. DSH 完成、失败或需要判断时，向原 Codex 聊天主动发送结构化消息。
4. Codex 在原聊天自动继续，读取必要证据并审阅；需要修改时，把反馈送回原 DSH 会话。
5. DSH 主动提问、Codex 回答也使用同一关联关系；权限升级仍由用户决定。

“直接通信”允许使用本地插件、消息队列和控制器，不要求两个窗口通过 GUI 互相打字。但不能把另起一个 Codex 决策会话、双方读取共享文件或用户手工转贴称作目标已经实现。

## 5. P0：隔离准备与源码核实

不启动模型即可完成：

1. 记录仓库 HEAD/status、系统、Node、Desktop、CLI、内置内核和 DSH Host 的实际版本。
2. 固定候选版本，下载到独立目录，只读审查其安装器、依赖、DSH profile 和控制器。
3. 查清候选是否要求旧版 DSH Web API；是否支持用户当前 Desktop 的鉴权 Gateway。遇到不兼容应单列，不关闭认证或修改 token 机制来绕过。
4. 确认桌面应用的真实启动 profile、插件格式及目标 Host。不要把 SDK profile 的成功安装当作 Desktop 已接入。
5. 明确测试数据目录、端口、进程归属和清理边界，准备对将修改的文件做逐文件备份。
6. 优先采用独立测试 profile 或局部加载；若确实只能修改用户正在使用的 Desktop profile，先做完代码和配置预览，再让用户选择测试窗口。

交付 `docs/desktop-coworker-qualification.md`：版本、源码路径、功能判断、哪些是文档声明/源码证据/实机证据，及尚未验证项。不要提前把状态写成“可用”。

## 6. P1：建立精确原聊天的只读连接

这是后续实施的门槛。先解决现有 proxy 传输失败：核对其连接到哪个实例、启动参数、端点来源和协议 framing。按官方支持的发现机制操作，不扫描内存、私有凭据或猜测其他聊天端点。

只读探测必须：

- 使用用户明确指定的测试聊天和准确 threadId；取得不到准确 ID 就说明缺少什么信息，不能按 cwd、标题或“最近创建”推断。
- 完成 initialize/initialized，再调用 thread/read，验证返回 ID 完全一致。
- 不调用 thread/start 创建替代会话，不发 turn/start，不加载别人的聊天历史。
- 对照当前桌面窗口，确认读取的是目标实例的同一会话。UI 无法核实时请用户作一次确认，不伪造确认结果。
- 记录候选使用的是“连接现有 App Server”还是“启动独立 App Server 访问共享存储”；这两种方式分开验收。

P1 失败时，完成独立代码/测试/诊断记录，停止后续有模型的场景。不要静默升级 CLI、修改全局 CODEX_CLI_PATH、打补丁到桌面应用或另起一个 thread 充当通过。

## 7. P2：验证原聊天自动唤醒

使用明确指定的测试聊天；用户未提供时，先完成其他准备，再集中请求测试聊天 ID 或让用户创建测试聊天。不能擅自用真实工作的聊天。

先使用程序生成的固定消息，排除 DSH 和模型服务的影响：

1. 注册精确 threadId 的回调，取得本地注册回执。
2. 测试聊天结束当前轮次，进入真正空闲，而不是让模型循环执行等待。
3. 后台程序等待约 60–90 秒；等待期间不调用 Codex 模型、不执行“保持在线”的模型请求。
4. 投递唯一测试消息，只触发一次自动验收轮次；优先使用官方 toolOutput 语义，使内容保持为工具数据。
5. 原聊天自动继续并识别标记，不需要用户再发“继续”；窗口中能看到对应消息/回复。
6. 再用两个相同 cwd 的测试聊天验证不串线。只持有一个明确目标 ID，另一个聊天不能被唤醒。

如果候选只能写入共享历史、要求用户重开窗口才看到结果，记录为“桌面可见、原窗口实时唤醒未通过”。如果它必须短暂取得 writer，单列用户忙碌时的冲突和释放行为；不能无提示抢占活动轮次。

P2 通过后才接真实 DSH。不能用候选作者环境的截图或单元测试替代本机测试。

## 8. P3：双桌面双向小任务闭环

DSH 端必须是测试 Desktop 会话，由该 Host/plugin 接收和执行；不能悄悄改成后台 SDK 并声称双桌面通过。后台 SDK 可继续作为兼容后端，但需要单列标识。

先使用一个已授权的模型路由。若独立 Desktop 测试 profile 未配置 Go，请给出配置预览和凭据引用要求，不把 SDK 凭据文件复制进去；不得把 Go Key 用于 DeepSeek 官方路由。

最小闭环：

```text
Codex 原聊天：提交一个读取测试文件的小任务，然后结束当前轮次
DSH Desktop：执行，提交完成摘要和证据引用
后台控制器：持久化关键事件，唤醒精确原 Codex 聊天
Codex：核对结果，向同一 DSH 会话发一个补充问题
DSH：回答，结果回到同一 Codex 聊天
```

再单独验证 DSH 在执行中主动提出一个问题，Codex 自动收到并回复，DSH 继续原任务。提问和完成不能都转成重新创建任务。

普通日志、工具调用和流式片段不唤醒 Codex；问题、失败、完成才按策略进入 outbox。权限请求必须展示给用户，不让另一个 Agent 自动决定升级。

## 9. 消息与交付契约

可以复用候选的存储层，但需要满足以下可见行为：

| 字段/机制 | 要求 |
| --- | --- |
| 身份关联 | 精确 Codex threadId、DSH sessionId、任务 ID；不凭标题/cwd选择 |
| 执行代次 | 同一任务每次分配新 executionId，不能把上一轮完成投给新一轮 |
| 消息身份 | messageId、replyTo、conversationId，支持关联问答与反馈 |
| 类型 | completed、failed、question、answer、review_feedback；普通 progress 本地保留 |
| 来源 | DSH 消息明确是外部工具数据，不伪装成人类指令或授权 |
| 内容 | 有界摘要、证据引用和必要状态，不传整个日志/对话/隐藏推理 |
| 生命周期 | pending → sending → acknowledged；不能确认则 delivery_unknown |
| 失败保存 | 投递前先保存结果，失败后仍可人工查看 |

超时/断线时，不清楚 turn/start 是否被接受就不得自动重发，也不得自动转发到另一个 App Server。不要宣称 exactly-once；确有幂等接口时才按其契约重试。

两个 Agent 的自动问答要有次数和用量上限，避免把日志轮询替换成无限互问。允许用户终止后续交接；停止后的晚到消息不能重新启动工作。

## 10. 生命周期与工作区

- Codex 模型轮次结束不能导致后台监听或 DSH 任务被关闭。
- 如果任务仍由现有 MCP 子进程拥有，应明确说明关闭应用仍会结束 Runtime；不要只 fork 一个监听器便宣称任务生命周期已独立。
- 本轮最小目标是两个应用打开时模型可空闲、重要事件可唤醒；关闭应用后消息保留与重开恢复另行验证，不承诺关机期间执行。
- Codex 审阅与 DSH 写入不能同时改同一工作区。保留 claim，优先独立 worktree。
- 不让两个编排器同时持有同一 session；不迁移真实任务去证明兼容。
- 禁止按进程名批量终止 node、codex 或 DSH。只清理由测试程序明确拥有的进程和目录。

## 11. 自动测试及实机验收矩阵

先用 fake controller/transport 验证身份、消息大小、重复事件、ACK 丢失、取消后不唤醒、忙碌排队、重启恢复。必要时本地 stub 模拟双方，减少模型消耗。

| 编号 | 实机项目 | 通过标准 |
| --- | --- | --- |
| D1 | 只读连接 | 确认精确原聊天及正确桌面实例，不创建新 thread |
| D2 | 空闲自动唤醒 | 原轮次已结束，收到一次消息后自动继续，无人工追加提示 |
| D3 | 原窗口同步 | 原窗口可见消息和验收结果，不要求通过新建/重开来掩盖同步问题 |
| D4 | 双向往返 | Codex → 原 DSH Desktop 会话 → 原 Codex → 原 DSH，身份不变 |
| D5 | DSH 主动提问 | Codex 收到并回复，原 DSH 任务继续 |
| D6 | 普通日志静默 | 模拟至少 100 条进度/工具事件，不产生 Codex 唤醒 |
| D7 | 同 cwd 多聊天 | 只唤醒明确绑定的原聊天 |
| D8 | 忙碌及并发 | 不抢占用户轮次、不启动重复验收，排队策略明确 |
| D9 | 断线和确认不明 | 结果保留，delivery_unknown 不自动重发 |
| D10 | 用户停止 | 停止后不继续自动交接，晚到消息不唤醒 |
| D11 | 重启边界 | 消息保留且不重复；未验证的应用退出情形明确列出 |

每项给出 PASS / FAIL / BLOCKED / NOT_RUN 及 mock/live 类别。第一次真实场景失败就先调查，不连续请求模型撞运气。初轮最多 6 次自动唤醒；DSH 的实际模型请求数若可获取则记录并设置可执行预算，不能把 turn 数当成 provider 请求数。

“等待期间零模型调用”的证据应来自可获得的调用计数/usage/事件时间线，而不是只看到模型没有输出。若平台没有足够遥测，写“没有观察到调用，零用量未能独立证明”，不捏造节省百分比。

## 12. 通过后如何接入本项目

D1–D4 未通过前，不替换正式安装。通过后选择一种清晰方案并说明理由：

1. 复用候选的消息/回调模块，接入现有 Orchestrator；保留 task/session 数据和 SDK 后端。
2. 将候选作为独立双桌面模式，采用独立状态目录和测试过的安装块；现有 SDK 模式继续可用。

优先方案 1，但不要为了坚持复用而依赖未验证的内核私有接口。若某候选只能接 DSH Web，必须交付明确的 Desktop 适配证据，不能沿用其 Web 成功结论。

只有后台监听和回调注册均成功，才将对应任务的 Skill 策略改为“提交后结束轮次”。普通监督不调用 wait/status/tail。能力不可用时明确告知用户需要手动回来，不在后台悄悄恢复模型轮询。

正式安装前准备完整可审阅的配置差异、文件备份和回退步骤。真实 Desktop profile、Codex 全局 MCP、应用升级或现有任务迁移属于最后的切换步骤；不要在 P0 调查时提前执行。

## 14. 直接执行指令

请按本任务书推进。先保存并尊重当前未提交修改，在隔离环境固定候选版本，优先调查 codex-dsh-bridge，必要时再评估 dsh-peer。先解决当前 Windows 桌面原聊天的只读连接，再证明原轮次结束后的自动唤醒和原窗口同步，然后验证 DSH Desktop 双向往返。

目标是停止 Codex 模型轮询，让普通日志留在程序内部、关键事件主动回到精确原聊天。不要以“另一个 Codex thread 能回答”“共享文件可读”或“重开桌面能看到历史”冒充目标通过。

直接完成可独立进行的源码调查、局部适配和测试。缺少测试聊天身份、需要用户操作或涉及正式安装切换时，将准备好的具体结果和所需动作一次说明；不要反复确认常规文件编辑。控制通道确实不可达时交付可复现诊断，不擅自升级或打补丁到应用。

保留现有 SDK＋OpenCode Go、Desktop 版本、凭据、M3 等真实任务以及回退能力。最终提交可审阅改动和证据报告，不自动提交或发布。
