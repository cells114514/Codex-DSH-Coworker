## 1. 当前状态及本轮目标

首版报告称 `npm run check` 386 项通过；真实 Windows SDK 握手、入队、事件、错误回传和退出链路已经运行，但所有模型 turn 均以 `MISSING_CREDENTIAL` 或 `AUTH 401` 失败，尚未获得成功的 assistant 回复。审批、问答、并发及部分恢复行为只有 mock 证据。

因此本轮目标是：修正事件生命周期缺口，定位认证问题，并完成可复现的真实模型任务、同任务续接及恢复验证。先完成代码和无账号测试；认证阻塞时继续其他独立工作，不以反复请求模型代替诊断。

保持版本组合：SDK Client / Runtime 均为已选定的 `0.2.2-rc.3`；用户 Desktop 保持 `0.2.1-rc.2`。版本变化只能作为有证据的独立建议，不自动升级、降级或替换 Desktop。不得把 SDK 成功与否归因于两个进程版本号不同。

本轮不增加动态模型路由、队列控制、单轮取消、任意 Desktop 会话附加或常驻后台服务。

## 2. 必修项 A：恢复之前订阅事件

重点检查 `src/sdk-runtime-manager.ts` 的 `acquire()`。当前源码可见顺序为：

```text
start → onRequest → initialize → resumeSession（恢复时）→ subscribe → startPump
```

恢复可能在 RPC 返回前发出新通知。订阅在恢复之后建立，会漏掉这些通知；“prompt 前已订阅”不能证明恢复安全。

实施要求：

1. 核实固定版本客户端的 subscribe/start/initialize 契约，在其允许的最早位置建立订阅；至少保证 resume 前订阅生效。
2. 处理 initialize 阶段的通知：能够完整收集就收集；有意过滤的类型明确列出，不声称不存在的覆盖保证。
3. 订阅、pump、registry、运行时状态应能处理 starting 阶段通知，不能简单前移一行后因只接受 ready 状态而丢弃。
4. 每个通知按原 wire 顺序进入持久化，再更新派生状态；恢复返回前发出的通知不能在首次 followup 之后才无序处理。
5. resume 失败、initialize 失败、SDK 中途退出时，关闭已建订阅，完成失败状态和进程清理，不留下假 ready 的 Runtime。
6. 不改为重发旧 prompt；不得伪造上游历史、seq 或补齐成功。

新增行为测试必须让 fake Runtime 在 `resumeSession()` 返回之前主动发出一条可识别的持久事件，并断言它被保存、去重正确、状态可见。单纯断言调用顺序不够。另覆盖恢复失败和初始化期间通知场景。

## 3. 必修项 B：正常关闭时的事件排空与 cleanShutdown

检查 `SdkRuntimeManager.dispose()`、`startPump()`、`onRuntimeExit()` 及 observed store 的完整生命周期。

当前代码先 `subscription.close()`，再关闭 SDK；且 `Promise.race([pump, Promise.resolve()])` 不会实际等待 pump 完成。这些写法需要通过行为测试核实是否导致队列中、处理中或退出期间的最后事件未落盘却记录 cleanShutdown。

目标行为：

- 正常退出必须区分“子进程退出已确认”和“观察记录已持久化完成”，不能仅凭 `client.close()` 成功判定记录完整。
- 在 SDK 允许的生命周期内保留通知接收，处理关闭前已入队及当前处理中的事件，再确认本地写入完成。
- 关闭有界，不能为等未知未来通知而永久阻塞。若 drain 超时或 SDK 机制无法证明完整排空，标记 partial/observation_gap，不写完整的 clean 状态。
- 泵、关闭流程和回调不能互相等待造成死锁；同一 task 清理幂等。
- 发生存储错误时，记录任务级降级，并阻止依赖完整视图的后续写入；不要只打印 handler 错误后继续宣称完整。
- 关闭失败不能从管理表删除所有占位后，允许旧进程退出未明时启动替代进程。

最小回归测试：最后一条事件正在延迟落盘时触发关闭；关闭期间又到一条终结事件；drain 超时；存储写入失败；重复关闭。分别断言最终正文可读或准确降级，不能出现 final pointer 存在而正文缺失且状态为完整。

本项是有具体源码线索的核查与修复任务。若某个风险已被其他层可靠防住，提交说明给出调用链和测试证据，不为了符合预设结论制造无用改动。

## 4. 定向复核：并发 acquire 与陈旧视图

不做全面重构，只针对以下两项增加可控并发测试，发现问题则修复：

1. `acquire()` 在检查容量后、注册 Runtime 前跨越异步操作，验证多个并发任务不会突破 `maxRuntimes`，同 task 不会重复启动、互相 dispose。需预留启动中容量或采用等价互斥机制，失败释放预留；不要把模型执行串行化。
2. `SdkConnectionAdapter.snapshot()` 当前以 generation 总和加 records.size 计算 revision。验证状态变化、交互解决、Runtime 移除/重建后 revision 能表达视图变化，不出现不同视图复用同 revision 导致陈旧写入被接受。必要时改成真正单调递增的 revision，增加 ABA 回归测试。

以上均保持原 workspace claim、cursor、所有权校验；不得绕过 preflight 来让测试通过。

## 5. 认证调查：先确定路由与凭据类型

`AUTH 401` 只说明当前 SDK 请求所用凭据被 provider 拒绝，不能据此认定 Desktop 账号登录无效，也不能直接要求购买或更换 API Key。

调查顺序：

1. 确认实际 SDK Runtime 版本和已加载 Profile。
2. 确认初始化时的 provider/model，以及它要求账号认证还是 API Key；模型可初始化不代表已经完成 provider 认证。
3. 使用固定版本官方文档和已安装公开源码，核实该 Profile 加载的认证模块、凭据解析方式、原生登录/配置入口。
4. 检查是否把 Desktop 账号凭据用于 API-key 路由、只复制了某个文件而缺少认证上下文、使用了错误 home，或存在显式环境配置覆盖。只输出来源类别和有无，不输出值。
5. 先做无需模型调用的检查；有合理修复依据后，再做一次有界只读模型验证。相同错误不要无变化重复调用。

操作边界：

- 不修改用户 Desktop home、登录状态、全局默认模型或现有配置，不重启/关闭用户应用。
- 不自动复制整个用户 home，不搜索无关文件中的 token，不输出凭据文件正文或环境变量全集。
- 当前脚本支持复制凭据文件，不代表本轮获得复制或重新分发秘密的授权。优先使用用户明确指定、已授权的 SDK 测试 home；认证需要额外用户操作时只询问缺少的具体步骤。
- 不更换 provider、付费路径或账号来隐藏原认证问题；使用其他路径必须明确说明并取得用户选择。
- 不请求用户把密钥粘贴进聊天或写入仓库；提供固定版本支持的原生配置步骤。
- 调查结果写成“已确认事实 / 尚未确认 / 下一步所需操作”，不能仅凭配置文件名判断认证机制。

用户已要求完成本轮修复和验收，可在现有明确授权的 SDK 测试凭据及路由范围内运行下述有限测试。若没有这样的测试环境，先完成所有代码、mock 和脚本工作，再集中说明认证阻塞；不要暂停独立可完成的工作。

## 6. 改造实机验收脚本

继续使用或拆分 `docs/operator-tools/sdk-live-acceptance.mjs`，不要另建一套脱离真实 MCP 路径的演示。

要求：

- 接受操作方明确提供的测试 home、任务场景和时间上限；不要默认搬运用户凭据。
- 明确区分脚本创建并拥有的临时目录，与用户提供的数据目录；只清理前者。
- 使用 `try/finally` 关闭 MCP、Bridge 和受控测试进程，失败时也清理；保留脱敏结果与失败类别。
- provider 认证失败时立即结束后续依赖模型成功的场景，不再把 followup 执行链路冒充续接验收。
- 每项输出 PASS / FAIL / BLOCKED / NOT_RUN，及 mock/live 证据类别。整体验收失败时退出码非零；BLOCKED 不能计入 PASS。
- 日志不输出问题全文、完整回复、API Key、原始凭据错误体或真实账号信息；任务/session 标识在公开报告脱敏。
- 执行耗时分开记录：MCP 连接、Runtime 初始化、prompt 接收、首次可见输出（若可观测）、任务终结、正常关闭。之前 60–85 ms 的 followup 是接收耗时，不能称为任务完成耗时。
- 总模型调用数有上限，不因等待超时自动重提输入，不自动重跑整个验收集。
- 支持只跑指定阶段；认证已确认后不需要每次重做所有真实测试。

## 7. Windows 实机验收矩阵

使用专用、可丢弃工作目录，先文本只读场景。成功回复可在本地比较，不要求把全文写入公开报告。

| 编号 | 场景 | 通过标准 |
| --- | --- | --- |
| L1 | 成功的单轮文本任务 | assistant 真实输出可读取，终结成功，finalMessageStatus 不为 terminal_missing_final，缓存指针可解析 |
| L2 | 同任务上下文续接 | 第一轮保存随机无敏感标记，下一轮不重复标记而要求回忆；同 task/session 正确返回，证明保留上下文 |
| L3 | 正常退出后恢复 | 关闭 Bridge、确认受控 Runtime 退出，重建 Bridge 后精确恢复原 task/session；真实回答保留的上下文；无重发旧 prompt |
| L4 | 用户问题 | 模型实际触发原生问题，Bridge pending 可见，由操作方通过 MCP 回答后完成；取消后旧回答失效 |
| L5 | 一次审批 | 用正常、无破坏性的操作触发原生审批，由操作方允许一次或拒绝；Bridge 不自动批准；结果和 pending 一致 |
| L6 | 双任务隔离 | 两个独立工作区同时有活动 Runtime，标记与事件不串线，容量上限有效 |
| L7 | 单任务 Runtime 异常 | 只中断脚本拥有的一个 Runtime，另一任务继续；受影响任务不显示成功，不重发输入，缺口/中断提示真实 |

顺序：先 L1–L3，再 L4–L7。若 L1 认证失败，L2–L7 记 BLOCKED，不继续制造同类失败调用。

L3 不能通过偷偷清空 registry、删除 owner/锁文件、改 taskId 或新建 session 来通过。如果保守的 observation_gap 政策阻止正常恢复，先分清是实际缺口还是关闭/订阅缺陷。无法证明完整就报告限制，不把检查关掉。

L4/L5 若当前环境无法自然触发，记录 NOT_RUN/BLOCKED 和原因，不通过放宽全局权限、伪造 pending 或自动允许来制造通过。向用户集中提出一次可执行的交互配合请求即可。

L7 只作用于明确由脚本启动和追踪的进程，不按名称批量终止 DSH/Node，不误杀 Desktop 或其他聊天的 Bridge。

macOS 本轮不强制；未跑就明确未验证。不得从 Windows 或 mock 结果推导跨平台通过。
